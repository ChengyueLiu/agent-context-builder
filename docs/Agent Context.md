# 一个 Agent 应该知道什么

Sep 29, 2026 · @Liu Chengyue

需要向 Agent 交代哪些内容，运行时从哪进入上下文，由谁在何时配置，以自动化科研 Agent 和配置 Agent 为例

## 1 引言

### 1.1 背景

Agent 已成为大模型的主要产品形态。编码、客服、数据分析、科研，几乎每个领域都在把模型接上工具，让它独立完成多步任务。搭一个 agent 的门槛很低：一段系统提示词加几个工具就能运行。

### 1.2 动机

提示词会随功能增加而失控。安全规则、业务流程、领域知识、用户偏好、历史教训被写进同一个文件；改一处牵一片；换模型往往要重写；agent 该记住的记不住，不该当真的却当真。

概念也在失控。元认知、情景记忆、长期记忆、合规、安全、skill，这些词来自不同体系，开发者说不清它们各指什么、彼此什么关系、该落在提示词的哪一部分。

两种失控的根源相同：动手之前没有回答几个基本问题。需要向 agent 交代哪些内容，每条是什么性质，谁来写，放在哪里，什么时候进入上下文，之后由谁维护。

### 1.3 现状

工业界已有局部方案。Claude Code、Codex、Gemini CLI 采用同一套做法：厂商维护按模型分版本的基础提示词；用户和项目用分级的说明文件补充；专业知识做成按需加载的 skill；agent 自己的记忆写入独立文件，由后台整理 \[4\]\[5\]\[9\]\[21\]。

学术界给出了分类。CoALA 把认知科学的记忆分类映射到语言 agent \[2\]；上下文工程综述把上下文形式化为指令、知识、工具、记忆、状态、请求六个分量 \[3\]；agent 记忆综述梳理了记忆的形成、演化与读取 \[43\]。

两者各答一半。产品给出了分层和存放的实践，论文给出了内容的分类；把"交代什么、放在哪、谁维护"作为一个整体回答的，尚无。

### 1.4 本文主张

Agent 的提示词、skill、记忆和配置是同一件事的不同部分，应统一在一张清单上设计。清单的每一行是一条需要交代的内容，每一列是关于它的一个决定：以谁的效力成立、在什么条件下适用、运行时从哪进入上下文、由谁在什么时候写到哪个目录。

本文涉及四个对象，它们经常被混为一谈（表 1）。方法是本文的主体，与任何框架无关；框架是方法的软件实现；具体 agent 是框架上做出来的实例；配置 agent 是框架的一个组件，把配置的流程自动化，它自己也是一个 agent。

表 1 本文的四个对象

| 对象 | 是什么 | 谁做 | 谁用 | 在哪一章 |
| --- | --- | --- | --- | --- |
| 方法 | 需要交代什么、运行时从哪进入上下文、谁在何时写到哪 | 本文 | 任何想做 agent 的人 | 2、3、4 |
| 框架 | 方法的软件实现：目录布局、六个地方的接线、平台级内容、配置工具、进度表、评测夹具 | 框架作者 | agent 设计者 | 4.6 |
| 具体 agent | 用框架做出来的一个实例 | 设计者、领域专家 | 终端用户 | 5 |
| 配置 agent | 框架的组件，执行配置流程；本身也是一个 agent | 框架作者 | 设计者、用户 | 4.7、6 |

第 2 章回答需要交代什么：四组九件事，每件展开为条目，每条带来源和适用条件。第 3 章回答运行时从哪进：六个地方，每个地方放什么、何时进，哪些交给机制。第 4 章回答谁在何时写到哪：六个阶段，每个阶段谁写什么到哪个目录、怎么写、写到什么算完，以及框架的交付物和配置 agent 的用法。第 5 章以自动化科研 agent 为例把三章的表填一遍。第 6 章以配置 agent 为例再填一遍，同时给出它的规格。结语讨论延伸。

## 2 内容：需要交代什么

Agent 是一个不停做决定的系统：看当前情况，决定下一步，执行，再看结果 \[2\]。它做对决定所必须知道的事，就是需要交代的内容。本章的结论是一张清单：四组九件事，每件展开为若干条目，每条带来源和适用条件两个标签。

### 2.1 只有上下文可以设计

模型每次被调用只能看到两样东西：训练进权重的知识，和这一次送入的文字。后者即上下文 \[1\]。权重不可更改，因此设计 agent 能控制的只有上下文里放什么。任何"向 agent 交代一件事"，最终都是一段文字存放在某处，在某个时刻被放进上下文。

这与招人相同。招一名博士，专业知识是他自带的，入职时不重教；入职后交代的是这家公司、这个岗位、这个项目的事。前者对应权重，后者对应上下文。本文只讨论后者。

### 2.2 方法：怎么确定要交代什么

需要交代的内容由决定的结构推出，分四组（表 2）。一个行动结论要从两类前提推出：一类说应当怎样，一类说事实如何；只有目标推不出行动，只有事实也推不出 \[49\]。应当的一侧按对象再分：关于产出的是岗位，由委托人交给 agent，agent 不商议它，只商议达成它的手段；关于过程的是规则，约束的正是这些手段 \[49\]。是的一侧按来路再分：干活之前配备的是事实，干活过程中产生的是处境，两者的来源、存放和刷新方式全然不同。每组之内按内容的对象划分出件，件之内按一个枚举的键列出条目。以“不编造数据”为例：它约束的是过程，属规则组；它不允许例外，属硬规则这一件；它防止的是产出失真，属硬规则里“产出的真实”这一类条目。四组与系统层的四种性质也对得上 \[56\]：机制对应硬规则及兜底它的机制，理解对应做法、协作规约、自我管理，偏好与责任对应岗位说明里由人保留的完成标准和授权。

表 2 四组的推导

| 组 | 前提的类型 | 再分的依据 | 回答的问题 | 例子 |
| --- | --- | --- | --- | --- |
| 岗位 | 应当 | 关于产出 | 要做成什么 | 论断清单逐条有证据 |
| 规则 | 应当 | 关于过程 | 过程中应当怎么做 | 不编造数据 |
| 事实 | 是 | 干活前配备 | 有什么、是什么样 | 工具的参数 |
| 处境 | 是 | 干活中产生 | 到哪一步了 | 上次实验的结果 |

条目按键枚举，而非凭经验罗列。每件事有一个天然的键：硬规则防止对某个对象的损害，键是保护的对象；做法服务于流程，键是流程的阶段；协作规约规定交互，键是交互事件；自我管理规定 agent 自己的循环，键是循环的环节。键定了，条目沿键列全，完整性再由三条线检查。需求一线：长程任务对系统的十二项需求里，能力侧每一项都要有内容告诉模型，十二项逐项落进九件事，无一落空 \[56\]。外部材料一线：Model Spec 的规则层 \[7\]、OWASP 的 LLM 风险清单 \[16\]、Claude Code 与 Codex 的主提示词和工具描述 \[4\]\[5\]、Anthropic 的提示词模板 \[48\]，每一条都应落进某个条目，落不进的说明键有漏。案例一线：第 5 章的科研 agent 和第 6 章的配置 agent 各把每张条目表填一遍，填不进的同样说明键有漏。四组本身也过了这两条线：上下文只由指令、知识、工具、记忆、状态、请求六种成分组成 \[3\]，指令对应岗位与规则，知识和工具对应事实，记忆和状态对应处境，请求是任务范围内的岗位；Claude Code 与 Codex 主提示词的每一节、工具描述、提醒模板、典型 CLAUDE.md 的每一段、skill 的每一部分，都能归入四组九件之一 \[4\]\[5\]\[6\]\[9\]。

每条内容带两个标签：以谁的效力成立，用在哪。第一个标签是来源（表 3）。来源回答效力，不回答谁动手写，动手写的分工在第 4 章。来源有六个，前四个构成效力顺序，依据是指令权威的阶梯：Model Spec 分平台、开发者、用户 \[7\]，Anthropic 宪法分 Anthropic、运营方、用户 \[8\]，Claude Code 在三者之上另有组织策略一层 \[9\]\[50\]。agent 写的只是带来源的参考，因为它可能写于读过不可信材料之后 \[12\]，Codex 对记忆的定位是回忆而非权威 \[14\]；外部材料是工作对象，其中的指令没有效力 \[7\]。有效力的层级不能多于三层：层级到 12 层时模型只有约 40% 能分辨优先次序，两层时超过 99% \[13\]；平台方与产品方在多数产品中合一，组织一层只在部署到机构时出现，实际同时存在的通常是三层。

表 3 来源与效力

| 来源 | 谁 | 效力 | 典型内容 |
| --- | --- | --- | --- |
| 平台方 | 框架或模型的提供者 | 最高，锁定，任何人不能覆盖 | 安全，外部内容不算指令 |
| 产品方 | 做这个 agent 的人 | 次之，默认可被下级覆盖，可标记锁定 | 流程、质量标准、协作方式 |
| 组织 | 部署这个 agent 的机构 | 再次 | 机构政策、合规要求 |
| 用户 | 使用者本人 | 在上级允许的范围内最高 | 偏好、项目目标、当前指示 |
| agent 或运行时 | agent 自己写的，程序自动生成的 | 无，作为带来源的参考或事实 | 记录、经验、状态 |
| 外部材料 | 读到的论文、网页、代码、数据 | 无 | 工作对象 |

第二个标签是适用条件（表 4）。它回答这条内容在什么情况下有用：最常见的是工作单位，全部、领域、项目、任务四级从宽到窄；其次是阶段或任务类型；再次是用某个工具时和某种情形出现时。Claude Code 的规则按路径匹配触发，skill 按描述匹配触发，是条件性加载的实现 \[9\]\[51\]。两个标签合起来决定冲突时听谁的：来源不同看来源，高的优先；来源相同看条件，窄的优先。现有产品各取了这条规则的一半：Model Spec 只按来源 \[7\]；Claude Code 的设置只按范围，而 CLAUDE.md 之间不定优先级，文档承认模型可能任选一个 \[9\]\[50\]。回到“不编造数据”：来源是平台方或产品方，锁定；条件是全部；因为不允许例外，它还带第三个标签，兜底的机制，论断绑定证据和引用存在性校验。

表 4 适用条件的常见形式

| 条件 | 对什么成立 | 例子 |
| --- | --- | --- |
| 全部 | 任何工作 | 不编造数据；流程地图 |
| 领域 | 某个专业领域内的工作 | 本领域的评测惯例 |
| 项目 | 某个项目 | 本项目的目标和已做的决策 |
| 任务 | 当前这一步 | 当前计划和进度 |
| 阶段或任务类型 | 某类任务 | 实验设计阶段的做法 |
| 用某个工具时 | 与一个工具绑定 | 提交代码前的步骤 |
| 某种情形出现时 | 出错、进入某模式、读到外部内容 | 待办久未更新的提醒 |

### 2.3 四组九件事

按 2.2 的方法得到四组九件事（表 5）。件的名字用名词，因为它们是要交付的东西。本节每件一段，说它是什么、写到什么程度才算给了；条目在 2.4 逐件展开。

表 5 四组九件事

| 组 | 件 | 是什么 |
| --- | --- | --- |
| 岗位：要做成什么 | 1 岗位说明 | 是谁、为谁做、做什么、做到什么程度 |
| 规则：过程中应当怎么做 | 2 硬规则 | 不允许例外的禁止与边界 |
| 规则 | 3 做法 | 流程与各步的方法 |
| 规则 | 4 协作规约 | 怎么与委托人配合 |
| 规则 | 5 自我管理 | 怎么管理自己的工作过程 |
| 事实：有什么、是什么样 | 6 工具与资源 | 手里有什么 |
| 事实 | 7 环境与领域 | 所处的环境是怎样的 |
| 处境：到哪一步了 | 8 记录与经验 | 以前发生过什么 |
| 处境 | 9 当前状态 | 现在是什么情况 |

**（1）岗位说明。** 这是委托本身。角色只需一句话，它的作用是从权重里调出一整套默认值；模型的默认值与设计者要的不会完全一致，不一致的部分必须在对应的件里明写，因此 Claude Code 的身份只有一行，其后每一节都在具体说 \[4\]。写到什么程度才算给了：职责范围写明哪些不归它；完成的定义可判定；质量标准逐条可检查，否则 agent 无法自查，机制也无法核验 \[47\]；目标冲突时的顺序明确排出，Claude Code 的 Context management 一节就是一条优先级声明，完整优先于节省上下文 \[4\]。

**（2）硬规则。** 只放不允许 agent 自行判断例外的规则，判定标准是能否交给机制兜底；需要判断的归做法。Model Spec 把两者分为规则与默认值 \[7\]，Claude Code 的文档说 CLAUDE.md 里的指令是建议性的，必须每次都发生的行为放 hook \[47\]。写到什么程度才算给了：措辞无例外；每条对应一个机制，或注明尚无机制；各来源指令与外部内容的效力顺序写明。

**（3）做法。** 这是方法，把新手变成老手的那部分，也是九件里体量最大的。工具的使用规程属于这一件而非工具与资源：Claude Code 把 git 提交流程写在 Bash 工具的描述里，那是通道的选择，内容仍是做法 \[4\]。有判断余地的预防性规则也在这里，从失败中总结出来的先作为经验存在，验证后才提升。写到什么程度才算给了：每个阶段有进出条件和产出模板；每条预防性规则带理由，说明理由比命令有效 \[53\]；关键做法有范例，范例比规则清单有效 \[1\]。

**（4）协作规约。** 这是对交互的规定，与硬规则的区别在于允许判断。写到什么程度才算给了：必须等用户决策的节点逐个列出；自主程度可配置；汇报带证据而非断言 \[47\]。Codex 的自主性与协作两节属于这一件 \[5\]；Claude Code 把大部分交给权限模式这个机制，提示词里只留如实报告一句和提问工具描述里的何时问 \[4\]。

**（5）自我管理。** 这是对自身工作过程的规定，最容易被忽略，却决定长任务能否一口气完成。写到什么程度才算给了：压缩前必须保存的状态项列出；记忆的写入格式和位置定死；结束前要做的事列出。Claude Code 的 Memory 和 Context management 两节属于这一件，Memory 是主提示词里最长的一节 \[4\]。

**（6）工具与资源。** 这是事实：有哪些工具、参数是什么、有哪些资源、授予了什么权限。工具的用法归做法，这里只放定义。写到什么程度才算给了：每个工具描述按对新人讲的方式写，含输入示例，示例把调用准确率从 72% 提到 90% \[55\]；目录条目不超过字符上限 \[51\]。按字数它是 Claude Code 全部内容里最重的一块 \[4\]。

**（7）环境与领域。** 这是关于世界的事实：领域怎么回事、委托人是谁、跑在什么 harness 上、模型是哪个。它与做法的区别在性质：方法有效力，事实只有真假和新旧。写到什么程度才算给了：运行环境的每个机制一句说明；领域知识分层，概览常驻，细节按需；外部材料标为数据。Claude Code 的 Harness 一节和环境消息属于这一件，领域知识它一条不写，因为软件工程在权重里 \[4\]。

**（8）记录与经验。** 这是干活过程中积累的，也是九件中唯一主要由 agent 自己写的。写到什么程度才算给了：原始记录只追加；每条经验带来源和状态，待验证、已采纳或已失效；提升为规则须经审批。Claude Code 自动记忆的四种类型、Codex 的记忆文件、AI Scientist v2 的实验日志属于这一件 \[9\]\[14\]\[44\]。

**（9）当前状态。** 这是此刻的事实，对人不言自明，对 agent 必须明说。写到什么程度才算给了：压缩后能从状态项恢复工作；每项有生成者。Claude Code 的环境块、git 状态快照、压缩后的摘要属于这一件 \[4\]\[28\]。

归类规则分两步。先判性质：是委托人要的（岗位）、执行时的约束（规则）、配备好的事实（事实），还是干活中产生的记录（处境）。再判对象：规则约束的是动作、做法、交互还是自身过程；事实关于手段还是环境；处境关于过去还是现在。一条内容只有一个性质和一个对象，因此不会两处都占。角色是唯一的例外，它是一句话概括，其展开内容按对象各归其位。

### 2.4 逐件展开

本节每件先给枚举的键，再给条目表（表 6 至表 14）。表的列是条目、写什么、来源、适用条件，硬规则多一列机制。表只列条目的类型，不填具体内容，具体内容见第 5 章；来源只标效力，谁动手写见第 4 章。

**岗位说明** 的键是岗位说明书的构成：头衔、汇报对象、服务对象、职责、目标、完成标准、质量标准、产出形式、冲突时的优先级（表 6）。对照材料是 Anthropic 提示词模板的任务背景与输出格式两段 \[48\]、Claude Code 的身份段与代码风格段 \[4\]。

表 6 岗位说明的条目

| 条目 | 写什么 | 来源 | 适用条件 |
| --- | --- | --- | --- |
| 角色 | 头衔与定位，一句话 | 产品方 | 全部 |
| 服务对象 | 为谁工作、向谁汇报、产出给谁看 | 产品方；用户 | 全部、用户 |
| 职责范围 | 负责哪些阶段，哪些不归它 | 产品方 | 全部 |
| 目标 | 本项目要达成什么 | 用户 | 项目 |
| 完成的定义 | 交付物是什么，什么状态算完 | 产品方；用户可覆盖 | 全部、项目 |
| 质量标准 | 逐条可检查的清单 | 产品方；用户可补充 | 全部、领域 |
| 产出形式 | 格式、语言、篇幅、模板 | 产品方；组织、用户可覆盖 | 全部、用户 |
| 优先顺序 | 目标冲突时先保什么 | 产品方；用户可覆盖 | 全部、项目 |
| 当前请求 | 这一次要做的事 | 用户 | 任务 |

## 3 运行：加载与机制

本章讲方法的运行一侧：内容写好之后，运行时怎样进入上下文。进入上下文只有六个地方（表 15），每个地方放什么、什么时候进，由内容的适用条件决定，来源和体量作次要因素，表 16 给出九件事各条目的分配。不允许例外的内容除了写进提示词还要交给机制，见 3.3 节。地方的设计以 Claude Code 为基准，它是目前公开材料最完整、也经过最大规模使用检验的 agent 提示词体系 \[4\]\[9\]。写好的内容存在哪个目录、由谁写，是第 4 章的事。

### 3.1 六个地方

六个地方各有性质，性质决定它适合放什么（表 15）。第七个地方是用户消息本身，当前请求由此进入，不由设计者写。

表 15 六个地方

| 地方 | 是什么 | 性质 | 放什么 | 时机 | Claude Code 的做法 |
| --- | --- | --- | --- | --- | --- |
| 系统提示词 | 每次调用的 system 字段 | 跨用户不变，可缓存，分量最重，预算最小 | 平台方、产品方写的、每步都用又小又稳的内容 | 常驻 | 按模型分版本，Opus 5.5 版 857 词，Sonnet 4.5 版 4260 词；环境信息放在它之外以保住缓存 \[4\] |
| 注入块 | 用户消息里带来源标签的块 | 按组织、用户、项目变；分量比系统提示词略轻 | 组织、用户、项目的常驻内容 | 常驻；项目内容在项目开始时 | CLAUDE.md 逐文件标明类型注入，块首写明效力；Agent SDK 用动态边界把按用户变的内容移到这里 \[9\]\[52\] |
| 工具描述 | 每个工具随请求发送的说明 | 与工具绑定，可延迟加载 | 工具定义与该工具的规程 | 随工具 | 20 到 24 个工具，4.7k 到 8.8k 词，git 流程在 Bash 描述内；延迟加载省 85% 的 token \[4\]\[55\] |
| skill | 目录常驻，正文触发时读 | 正文有上限，压缩后只留前 5k token | 按阶段、任务类型、领域才用的方法和知识 | 进入阶段或触发时 | 目录占上下文 1%，每条不超过 1536 字符；正文不超过 500 行，附件只引一层 \[6\]\[51\] |
| 文件与索引 | 磁盘上的文件，靠读取和检索进入 | 无上限，agent 可写 | 体量大或不断增长的记录、经验、资料 | 需要时；索引常驻 | 记忆索引前 200 行常驻，主题文件按需读；压缩后从磁盘重读 \[9\]\[28\] |
| 运行时提醒 | 程序每轮生成的块 | 体量小，按情形触发 | 会变的状态，情形触发的提示 | 每轮，或情形出现时 | 约 110 条模板：环境、git 状态、待办催促、计划模式、外部内容警告；压缩摘要固定五段 \[4\]\[28\] |

常驻内容越少越好。上下文越长，模型对其中内容的回忆越差 \[17\]；指令超过数百条后遵守率明显下降，且偏向靠前的指令 \[18\]。因此体量大、按情况才用的内容采用渐进披露：目录常驻，正文触发时读，附件需要时读 \[1\]\[6\]。写多少也由此决定：只写模型默认做不对的，每一行都问一句删掉会不会出错，答案是不会就删 \[47\]。Claude Code 给新模型的主提示词比旧版短五倍，砍掉的正是新模型已经会的语气、待办和任务做法 \[4\]。

另有四点影响效果。顺序：很少变的内容放前，会变的放后，前缀稳定才能命中缓存，命中缓存的输入价格约为十分之一 \[19\]；按用户变的内容移出系统提示词的代价是分量略轻 \[52\]。出处：组织、用户和项目的内容每块标明来源文件，外部内容标明为数据而非指令，不与产品方的内容混合 \[9\]。情形触发：出错、进入某个阶段、读到外部内容时才需要的提示，用运行时提醒按情形注入，不常驻 \[4\]。压缩：长任务中上下文必然被压缩，压缩后系统提示词保留，根 CLAUDE.md、记忆索引和计划文件从磁盘重读，已调用的 skill 只保留前 5k token，按路径触发的规则丢失，对话中的内容可能丢失 \[28\]。因此重要状态必须写入文件，skill 的关键指令放在开头，压缩摘要按固定结构写：任务概述、当前状态、重要发现、下一步、需保留的上下文 \[4\]\[28\]。

分量和地方要分开看。用户写的硬约束走注入块，分量比系统提示词略轻，补救办法是块首写效力声明，真正不能违反的交给机制，不靠换地方。

### 3.3 交给机制的部分

写进提示词的内容只是引导，模型不必然照做。硬规则的每一条除了写进系统提示词，还要交给一个机制：权限、沙箱、hook、只读、自动校验 \[9\]\[15\]\[16\]。Claude Code 的文档把这条写成规则：CLAUDE.md 里的指令是建议性的，必须每次都发生的行为放 hook；模型不加指令也能做对的行为，删掉指令或改成 hook \[47\]。自动模式下另有一个分类器模型在每个动作前审查，拦下越权、陌生基础设施和由外部内容驱动的动作 \[47\]。

提示词里仍应说明机制的存在，使 agent 理解某些操作为何被拦截 \[4\]。写法上有两条经验。说明理由比命令有效：“不要用省略号”不如说明这段文字会被语音合成朗读 \[53\]。强调词要省着用：新模型对 CRITICAL、MUST 一类词反应过度，全篇强调等于没有强调 \[47\]\[53\]。机制本身的设计退出本文范围。

表 16 按地方分组即得要写的文件：系统提示词、注入块、工具描述、skill、文件、运行时提醒，以及交给机制的一组。这些文件由谁在什么时候写到哪个目录，是第 4 章的内容。

## 4 配置：写入的生命周期

### 4.4 写入、验证与淘汰

人写的内容先写检查项再写正文，agent 写的内容分记录和提炼两种对待。运行中写的是原始记录，自动写、只追加；事后写的是提炼的内容，需要完整经历才能判断取舍，并在后台进行以免占用运行时延迟 \[14\]\[20\]\[21\]。Anthropic 对 skill 的建议是先写评测 \[6\]，对 CLAUDE.md 的建议是像代码一样对待，出问题时复查、定期修剪、改动后观察行为是否真的变了 \[47\]。没有检查项的内容不进常驻的地方。

验证和修改权限按来源分四种。平台方与产品方写的随版本修改，每次改动逐行消融、按模型评测后发布；Anthropic 曾因一句限制字数的话导致 3% 的性能下降，此后改为按模型评测并逐步放量 \[22\]。组织写的由组织管理员修改，用户不能覆盖其锁定项 \[50\]。用户写的由用户随时修改，产品更新不触碰，agent 仅在用户明确要求时代写 \[9\]。agent 写的分两种：原始记录只追加；提炼的内容须验证或审批后生效 \[21\]\[23\]。提炼的条目按固定格式写，规则、为什么、怎么用三段，成功和纠正都记 \[9\]；整理时合并近似条目、相对日期改绝对、修剪索引，与用户写的内容冲突时只标记不改写 \[9\]\[23\]；修改时增量修改而非整体重写，整体重写会把内容压没 \[24\]。agent 自写的 skill 实测平均为负收益，精选的 skill 平均提升 16 个百分点 \[25\]，因此从记忆到规则的提升必须经人审批，Gemini CLI 的做法是把候选条目放进审批收件箱 \[21\]。硬规则和质量标准任何人都不能修改，尤其不能允许 agent 修改评判自身的标准，否则自我改进最省力的路径就是降低标准 \[26\]。

淘汰的主线是模型默认值。每条人写的内容都是相对模型默认行为的增量：或者覆盖默认值，或者复述它。复述的部分在模型升级后应删除，覆盖的部分才是长期资产。Anthropic 的说法是 harness 里每个组件都编码了一个关于模型做不到什么的假设，模型进步就该拆掉相应的脚手架 \[54\]；Claude Code 从 v2.0 的一整篇长提示词砍到 v2.1.20 的 269 token，就是这条原则的实施 \[4\]。因此每条内容在写入时标明它覆盖的是什么默认行为，模型升级时按此逐条重测。淘汰的方式有五种：版本替换、用户删除、标记失效、长期未用自动清理、合并去重。原始记录不删除，错误的结论标记失效而非抹去，以便追溯 \[27\]；提炼型内容按使用频率淘汰，Codex 删除 30 天未用的记忆 \[14\]，Claude Code 在后台整理时修剪索引 \[9\]。

## 5 案例一：自动化科研 Agent

### 5.1 定位

该 agent 辅助科研人员完成研究，目标是一名有丰富发表经验的博士后的水平：知道怎么做，能独立完成，用户无需过多干预。用户是导师，给方向，在关键节点决策。程序安装在用户电脑上，随版本更新。

岗位说明和协作规约里有四个产品决定，本章取表 29 的默认值。

表 29 四个产品决定

| 决定 | 默认值 | 能改的人 |
| --- | --- | --- |
| 职责范围 | 从调研定位接手，到论文初稿交付；选题方向和投稿决定归用户 | 产品方，用户可改 |
| 完成的定义 | 论断清单逐条有证据支撑或已确认无法支撑，附可复现的实验记录和论文初稿；负结果也是合格的完成 | 产品方，锁定 |
| 优先顺序 | 质量优先于预算，预算优先于时间；影响论断的决定宁可问不猜 | 产品方，用户可改 |
| 自主程度 | 阶段内自主推进，阶段间的检查点等用户；研究问题、方案、投稿三处必须用户拍板 | 产品方，用户可改 |

它与编码 agent 的根本差别在两件事上：岗位说明里的质量标准，环境与领域里的领域知识。Claude Code 这两处几乎空着，因为写代码的完成有外部判据，测试过了就算过，而软件工程在权重里 \[4\]\[47\]。科研没有“测试过了”这种判据，领域里什么算贡献、常用 baseline 是什么也不在权重里，因此这两件必须由产品方自己写，也是本章最厚的两张表。

它要解决三个问题：agent 不知道如何做研究，执行过程不可靠，成本高。本章回答第一个；第二个只写到哪些内容交给机制；第三个只体现在地方和时机的选择上。

| 项目期 | agent 起草，用户确认 | 研究问题、目标会议、论断清单、已排除方向、文献库 | 项目目录 | agent 起草章程，用户确认 |
| 运行期 | agent、运行时 | 实验记录、尝试与失败、阶段产出、状态、待验证经验 | 项目目录、运行时 | 自动 |
| 事后与升级期 | 用户、产品方 | 经验审批、失效标记、模型升级重测 | 用户目录、发布包 | 审批收件箱，配置 agent 重测 |

**存储。** 发布包内放系统提示词、工具描述、阶段 skill、内置领域 skill、外部规则 skill，随版本整体替换。部署到机构时，组织策略目录放机构的合规要求与锁定项。用户目录放用户配置、用户补充的领域 skill、经验库及待审区，产品更新不动。项目目录放章程、实验记录、阶段产出、决策记录、项目资料，随项目归档。运行时放待办和状态。

**变更与淘汰。** 产品方内容随版本替换；用户配置由用户随时改；章程只有用户确认才能改；记录只追加，阶段产出回退重做时新写一版、旧版保留；经验经审批生效，长期未被检索到的归档。

### 5.5 为什么诚信靠机制，经验严把写入

清单中有两处的答案与其他内容差异最大，各有实测依据。

**科研诚信。** 提示词里的“不要编造”实测无效：数据缺失时七个模型全部自行合成数据，提示词只影响是否披露 \[30\]。有效的是结构性做法（表 41）。机制本身的设计属于可靠性问题，另文讨论。

表 41 科研诚信的机制与依据

| 机制 | 防什么 | 依据 |
| --- | --- | --- |
| 论断绑定到运行日志或检索结果 | 编造数据、编造引用 | ScientistOne 用证据链做到 337 条引用零幻觉，基线系统最高 21% \[31\] |
| 引用存在性自动检查 | 编造引用 | Agents4Science 约 44% 投稿含可疑引用 \[32\] |

**经验。** agent 在阶段或项目结束后在后台提炼经验，成功和失败都提 \[37\]。提炼后先进入待审区，每条带来源；用户确认或在后续项目中验证有效后才生效 \[21\]\[23\]。写入把关严，是因为证据一边倒：跨项目经验库提升论文质量的证据目前很薄 \[40\]，错误经验被后续任务照抄的证据很确定 \[38\]\[39\]，agent 自写 skill 平均负收益而人写的提升 16 个点 \[25\]。经验的验证与提升另文讨论。

### 6.3 加载与配置

它自己的内容按第 3 章的规则分到地方：岗位说明、硬规则、流程地图、协作默认值、自我管理、机制说明进系统提示词；九件事各一个访谈与归类 skill，进入某件时读；进度表、待确认区、目标 agent 的材料走文件与索引；当前阶段与进度走运行时提醒。它的配置发生在框架期，由框架作者手工写，这是唯一不能用配置 agent 完成的配置，因为它还不存在。上线之后，它的维护走 4.4 节的规则，与任何具体 agent 相同。

### 6.4 边界

它起草，人审批，这条边界不能动。依据与 4.4 节相同：agent 自写的 skill 实测平均为负收益，人写的精选 skill 平均提升 16 个百分点 \[25\]；错误的经验会被后续任务照抄 \[38\]\[39\]。它的价值在于把归类和放置这两步做成机械操作，把人的时间留给判断：哪些是锁定项，默认值对不对，检查项够不够。它不替人决定这些。

## 7 结语与展望

提示词越写越乱，是因为四个对象被混在一起：方法、框架、具体 agent、配置 agent。方法回答需要交代什么、运行时从哪进、谁在何时写到哪；框架实现方法；具体 agent 是框架上的实例；配置 agent 是框架里执行方法的组件。四者分开之后，每条内容都有自己的件、来源、条件、地方、目录和阶段，系统提示词就只剩下真正需要常驻的那一小部分。

这套方法不依赖特定框架。四组九件事来自实践推理的前提结构和内容的对象，六个来源来自指令权威的阶梯，六个地方来自现有 harness 的通道，六个阶段来自内容变得可知的时间。换一个业务，只是表里的内容不同，行列不变；第 5 章和第 6 章用两个完全不同的 agent 验证了这一点。

行列固定意味着配置本身可以交给一个 agent，第 6 章给出了它的规格。它读入现有的提示词、skill、配置和记忆，把每一段归到九件事中的某一条，标出来源和适用条件，分到地方和目录，把该锁定的标出来，把常驻的压到最小，最后报告每个阶段的进度。做出来之后，它是框架的第一个交付物。

本文未展开四件事，各自是一篇文章：科研流程具体分几个阶段、每个阶段的做法和标准写什么；交给机制的内容如何设计；agent 提炼的经验如何验证、如何向更宽的范围提升；配置 agent 的访谈 skill 和评测怎么写。本文本身可拆成三篇：方法（第 1 至 4 章）、科研 agent（第 5 章）、配置 agent（第 6 章）。
