# Agent Context Builder

解决两个问题：

1. 定义一个 agent 到底要说明哪些东西。要全，不能漏。
2. 这些东西按什么逻辑组织。要稳，写的人顺着目录就能写下去，不会不知道某段内容该放哪、该改哪。

答案做成一份预置好的大纲。人只填具体内容，填完就生成定义这个 agent 需要的全部文件。

## 三部分

| 目录 | 是什么 | 状态 |
| --- | --- | --- |
| [docs/](docs/) | 方法文档，以及 Anthropic 的参考资料（[docs/anthropic/](docs/anthropic/)） | `Agent Context.md` 是早期草稿，还没有按现在的大纲更新 |

| agent/ | 配置 agent：辅助人填写和维护 | 还没开始 |

## 共用的部分

- [template/default.yaml](template/default.yaml)：大纲。定义一个 agent 要写的全部栏目、每一栏写什么、生成到哪里。要增删栏目，改这个文件，builder 不用改代码。
- [examples/](examples/)：示例 agent。`research-agent` 是自动化科研 agent。
- [reference/](reference/)：论文与调研笔记。

## 大纲

定义一个 agent，就是组织好一批东西：它预先拿到的资源、运行中产生和维护的东西、它需要知道的基础信息，再加上保证它安全、可靠的机制。最后合成一份系统提示词，并允许它按需去读其余的东西。

左侧目录就是这个结构，顺序和系统提示词一致：

| 组 | 页面 | 写什么 |
| --- | --- | --- |
| 功能性配置 · 工作说明 | 身份与目标、工作流程、交付与验收、用户协作、原则与红线 | agent 自己的工作要求：是谁、怎么做、怎样算做完、怎么和用户配合、怎么取舍 |
| 功能性配置 · 环境说明 | 环境说明（单独一页） | 在哪干活、周围有什么、系统运行时告诉它什么。开发者和系统提供，agent 只读 |
| 功能性配置 · 资源说明 | Skill、知识、工具、帮手 | 能拿来用什么。跟着 agent 走，开发者维护，agent 只读 |
| 功能性配置 · 运行时管理规则 | 记忆管理、项目管理、产出物管理 | 记忆：agent 脑子里记着的要点（项目概况、进展、参考、用户、反馈），开工和压缩后由系统加载；项目管理：规划和待办，每项带状态；产出物：最终交付、过程成果、工作记录。开发者定规则，agent 运行中产生、维护与使用 |
| 非功能性配置 · 安全与合规 | 信息安全、人身与社会安全、合规 | 防攻击和泄露；防止伤到用户、第三方和社会；遵守法律、行业规定和伦理 |
| 非功能性配置 · 可靠性 | 事前预防、过程纠正、事后改进 | 上限和系统保证；关卡、评审、出错处理、压缩、自动提醒；复盘、检验用例、定期复查 |

“这一次具体做什么”不在定义里，由用户每次交任务时给。

系统提示词只放每次都要、基本不变、是原则的内容。经常变的、细节的、只在某类任务里用的，放进 skill。

一段内容该写在哪，先问：把它去掉以后，agent 还知不知道要做什么、怎么做？

- 不知道了：功能性配置。原则写进“工作说明”里对应的一页；某类任务的做法写进那一类的 skill；查阅用的资料写进知识；只关于某个工具的写进那个工具。
- 照样能做，但可能被攻击、泄露、越权：信息安全；可能伤到人：人身与社会安全；可能违法违规：合规。
- 照样能做，但出错时没人发现、没人纠正：可靠性。
