## 对我们最重要的 5 篇

**1. Evaluating AGENTS.md（2602.11988）**
它是唯一一篇对我们要编译出的那类产物做受控评测的论文，评测对象是仓库级上下文文件。有三点直接影响我们：
- 由 LLM 生成的上下文文件不提高成功率，SWE-bench 上 −0.5%，CTXbench 上 −2%。开发者手写的平均 +2.4%。两种都让成本上升 20%–23%。
- 文件里的指令确实被遵守，所以每多一行都会改变行为、增加步数。
- 仓库概览不帮助定位文件。把 README 和文档删掉后，LLM 生成的文件反而 +2.7%，说明多数内容只是复述环境里已有的信息。

由此三个推论：
- 淘汰要沿两条线进行：复述模型默认值的删，复述环境里已有信息（README、代码）的也删。
- 配置 agent 不能整篇生成后直接用。
- 2.3（7）“概览常驻”需要评测来支撑。

**2. IHEval（2502.08745），与 Control Illusion（2502.15851）合读**
文档的冲突规则（2.2）是“来源不同看来源，来源相同看条件，窄的优先”。它默认模型能按效力次序裁决冲突，这两篇正好检验这个前提，结果是不能：
- IHEval 中，有冲突时各模型的准确率为 14.0%–70.0%。无冲突时为 78.8%–91.0%。
- 明确告诉模型“请按层级优先”的提示没有用，GPT-4o 从 70.0 变成 67.2。
- 谁的措辞更严厉，模型就听谁的。冲突指令措辞变严厉后，准确率从 31.8 降到 9.3。
- Control Illusion 发现，“CEO 要求”“专家共识”这类社会权威说法比 system/user 角色更有效，GPT-4o-mini 从 47.5 升到 77.8。

因此：
- 冲突应当在编译时由 builder 裁决，只把裁决结果放进上下文。
- 运行时仍可能出现的冲突交给机制处理。
- 块首效力声明只算弱辅助。
- 低效力的内容（agent 写的、外部的）要检查措辞，不能用强调词和权威说法。

**3. Revoked but Still Authoritative（2609.08258）**
它检验的正是文档 4.4 里的“错误的结论标记失效而非抹去”和经验的状态字段。测了五个记忆系统，结果如下：
- 被撤销的事实全部仍被检索出来（81/81），且排在替代它的新事实前面。
- agent 因此执行不安全动作的比例是 43.1%。
- 在提示词里要求“忽略已被取代的事实”，只降到 37.2%。原因是检索结果里看不出哪条已被取代。
- 在存储或检索层过滤，降到 0/1620。

结论：“已失效”这个状态必须由机制在内容进入上下文之前执行，不能靠提示词。对 builder 来说，就是失效卡片一律不进编译产物，替代卡片必须写明它取代了谁（`supersedes`）。

**4. What Prompts Don't Say（2505.13360）**
它给“只写模型默认做不对的”（3.1）和“升级后删复述默认值的内容”（4.4）提供了定量依据，也给出了一个修正：
- 真实开发者提示词里有 65.2% 的需求不写模型也能猜对，支持删减。
- 但没写的需求在模型更新后更不稳：22.9% 的情况会退化，5.9% 的需求下降超过 20%，约为写了的需求的 2 倍。
- 连同一模型的静默快照更新也会造成退化。
- 把所有需求都写上，反而会让表现下降 19%。
- 条件类需求最难被猜中，只有 22.9%。格式类最容易，70.7%。

由此有三个改法：
- 删正文，但留检查项。
- 模型的静默更新也要重跑检查。
- 访谈时重点挖掘“某种情形出现时”的条件类需求。

**5. Configuration Smells in AGENTS.md（2606.15828）**
100 个热门仓库里，91% 的配置文件至少有一种“坏味道”。六种坏味道几乎一一对应我们方法里的一条规则：

| 坏味道 | 占比 | 违反的规则 |
| --- | --- | --- |
| Lint Leakage | 62% | 已交给机制的规则不该再写进提示词（3.3） |
| Context Bloat | 42% | 常驻越少越好（3.1） |
| Skill Leakage | 35% | 条件性内容不该常驻（3.2） |
| Init Fossilization | 24% | LLM 起草的内容没经人审（4.4、6.4） |
| Conflicting Instructions | 28 例检出，16 例确认 | 冲突检查 |
| Blind References | 16 例检出，14 例确认 | 索引条目要写明用途 |

这篇论文既从外部验证了文档 3.2 和 4.4，也可以直接转成 builder 的第一批 lint 规则。

## 与现有文档矛盾或需要补充的发现

按文档章节排列。每条写明文档原意、新证据和建议改法。

1. **2.2“有效力的层级不能多于三层……两层时超过 99% [13]”的说法过强。**
   - ManyIH 原文里的 >99%，引的是 GPT-5 system card 在特定两层评测上的数字，例如系统提示词提取，不是两层冲突的一般结论。
   - 两层冲突在 IHEval 中为 14.0%–70.0%，在 Control Illusion 中平均为 9.6%–45.8%。这两篇测的是 2024 年那一代模型。
   - 较新的 IH-Benchmark（2607.25987，37 个模型）合规率为 20.5%–98.2%，并发现“system 压得住 user，不代表 user 压得住工具输出”。
   - 建议改为：层级少是必要条件而非充分条件，冲突要在编译时裁决（第 2 篇）。

2. **2.2 的冲突规则与 3.2 末尾的“块首写效力声明”是在指望模型自己裁决。**
   - IHEval 里加“按层级优先”的提示没有用，甚至略降（70.0→67.2）。
   - 建议：冲突规则改由 builder 或配置 agent 在编译时执行，只把裁决结果放进上下文。“块首效力声明”降格为弱辅助。唯一会在运行时出现的冲突（用户当前请求对上锁定项）由机制兜底。

3. **3.3“强调词要省着用”不只是文风问题。**
   - 模型听措辞更严厉的一方（IHEval：31.8→9.3），也听“权威、专家、共识”这类说法（Control Illusion）。
   - 建议在表 7“指令体系”一行补一条：agent 写的记录、经验和外部材料不得使用强调词或权威说法来抬高自己的分量。这是“不伪造来源标签”的延伸。
   - 另一方面，真实系统提示词里有 4,725 行强调句（2609.31575），说明业界普遍违反这条建议。

4. **表 7、表 31、表 44 把“来源标注”列为“外部内容是数据”的兜底机制，这一项不成立。**
   - Design Patterns（2506.08837）认为分隔符和标签是启发式手段，不提供保证。
   - 真正的机制是隔离模式：先定计划再读不可信数据（Plan-Then-Execute）、特权 LLM 不看原文（Dual LLM）、每份不可信数据单独处理（Map-Reduce）、读完后收窄工具权限。
   - 科研 agent 持续读论文和网页，应采用这些模式。

5. **4.4“错误的结论标记失效而非抹去”需要加执行机制。**
   - 状态写在条目上不够，必须在编译或检索时把失效条目过滤掉。prompt 加固只把不安全率从 43.1% 降到 37.2%，存储层过滤降到 0%（第 3 篇）。
   - 新条目必须写明它取代了谁。
   - 顺序不明时并存并报冲突，不能按顺序猜。他们的守卫早期版本按结果顺序裁决，使不安全率从 0% 变成 100%。

6. **3.1 与表 16 的“记忆索引常驻”，以及 3.1 的压缩摘要，都是投毒通道。**
   - 2606.04329 的结果：把记忆快照装进系统提示词的 agent（HERMES），投毒在后续会话中的生效率是 64.70%；只通过工具读取记忆的 agent（OpenClaw）是 17.40%。
   - 经由压缩投毒的成功率高达 85.17%。
   - 建议：常驻的索引只收已审批的条目，待审条目按需读取；压缩摘要保留来源标签，外部内容不能不加标注地进入“重要发现”；记忆写入策略必须逐项列明，模糊的写入策略本身就是漏洞。这一点支持文档“记忆的写入格式和位置定死”。

7. **4.4 的淘汰只沿“模型默认值”一条线，需要补两条。**
   - 第一条：复述环境的内容也该删。所谓复述环境，指 agent 自己能读到的 README、代码、文档（2602.11988）。
   - 第二条：环境漂移会触发更新。Codified Context（2602.20478）里主要的失效方式是规格随代码变化而过时，需要把卡片绑定到代码路径并做漂移检测。
   - 删除时保留检查项（2505.13360）。
   - 不只在宣布换模型时重测，静默快照更新时也要重测。

8. **4.4“人写的内容先写检查项再写正文”与 EvalGen 的“标准漂移”冲突。**
   - EvalGen（2404.12272）发现，人要先看过输出、动手打分，才能确定评判标准，而且会回头改先前的打分。
   - 建议改为：先写检查项草稿，看过真实输出后修订；检查项要有版本，允许变化。

9. **2.3（3）“范例比规则清单有效 [1]”的证据有分歧。**
   - AgentIF（2505.16944）中，以范例形式给出的约束遵守率最高，为 69.2%–87.0%。
   - GEPA（2507.19457）发现，只优化指令胜过指令加 few-shot 一起优化，而且泛化更好。
   - AWM（2409.07429）发现，带占位符的抽象流程胜过检索具体范例，元素准确率 +5.0，步骤成功率 +4.0。
   - 建议改为：输出格式类内容用范例，流程类内容用带占位符的抽象例程，加不加范例由消融决定。

10. **2.3（6）“工具描述含输入示例，示例把调用准确率从 72% 提到 90% [55]”需要限定条件。**
    - MCP 工具描述研究（2602.14878）在 MCP-Universe 上做了消融：去掉示例从未显著降低表现。
    - 把描述补全，任务成功率中位数 +5.85 个百分点，但执行步数中位数 +67.46%，16.67% 的情况退化。
    - 简短而有针对性的描述与完整描述在统计上无差别。
    - 建议：示例用于参数格式复杂的工具；默认要写全的是用途、何时使用、限制、参数四项。

11. **3.1“常驻越少越好”得到加强，但“偏向靠前的指令 [18]”需要限定适用范围。**
    - 加强的证据：
      - 即使检索完全正确，仅长度就使表现下降 13.9%–85%（2510.05381）。
      - 真实 agent 指令平均 1,723 词、11.9 条约束，每条都满足的比例最高只有 27.2%，超过 6,000 词时接近 0（AgentIF）。
      - 上下文文件让成本上升 20% 以上（2602.11988）。
    - 需要限定的证据：在 25–500 行、只测一条指令的设置下，位置和文件大小都没有可检出的效应（2605.10039）。
    - 更大的效应是会话内衰减：每多生成一个函数，遵守的几率乘以 0.944。任务类型的影响也更大：遵守率在 45.1% 到 84.4% 之间。
    - 建议：
      - 位置论证只在指令数量多、上下文长时成立。
      - 需要全程成立的规则，用运行时提醒或 hook 在会话中重申。文档里的运行时提醒目前只放状态和催促，应补上“硬规则重申”。

12. **3.2“某种情形出现时 → 运行时提醒”得到支持。**
    - AgentIF 中条件类约束的成功率最低，为 35.0%–41.5%。这类失败里超过 30% 是模型误判了条件是否成立。
    - 条件应由 harness 判断后再注入，不要在系统提示词里写成“如果 X 则 Y”。

13. **3.1 固定五段的压缩摘要应改为可评测、可调的模板。**
    - ACON（2510.00615）：朴素的 LLM 摘要让 AppWorld 准确率下降 12.5 个点（56.0→43.5）。优化后的压缩指南恢复到 56.5，峰值 token 减少 26%–54%。
    - 优化出的指南里有一张“运行时值表”，记录文件路径、ID、API 参数，以及决策和理由。
    - 建议在五段之外加一段“关键变量与运行时值”，并把模板当作自我管理的一张可评测卡片。

14. **4.4“修改时增量修改而非整体重写，整体重写会把内容压没 [24]”需要限定。**
    - Auto-Dreamer（2605.20616）在后台对一个区域整体重写，同时保留原始日志作为证据。结果：
      - ScienceWorld 成功率 41.1%，ReasoningBank 为 30.9%。
      - 记忆体积 6.9k token，ReasoningBank 为 155.1k。
    - 建议改为：没有证据链接的整体重写会把内容压没；以原始记录为依据、新条目链接回来源的区域重写是可行的。

15. **5.5 和 4.4 引 ReasoningBank [37] 支持“提炼经验”，需要补一个反证。**
    - 在相同 token 预算下比较（2606.15017，EMNLP 2026），AWM、ASI、ReasoningBank 都没有赢过不带模块的基线。
    - WebArena 上，基线 44.78%，消耗 73.6K token；ReasoningBank 39.33%，消耗 82.6K。
    - 这加强了文档“跨项目经验库证据薄”的判断。
    - 建议：任何记忆或经验模块，都要和同预算的基线比较后再上线。

16. **4.4“提炼型内容按使用频率淘汰”还应加一条“复用时重新验证”。**
    - 验证缺口综述（2608.05179）指出，复用一条存下来的经验，等于默认重申一个在别的条件下做过的验证（“审计债”）。
    - 建议：经验在新的条件下被复用时，应触发重验或至少标注来源条件，不只是按时间过期。

17. **4.4“不能允许 agent 修改评判自身的标准”得到强化，并需要补一点。**
    - DGM（2505.22954）中，agent 不顾“不要改动特殊 token”的明文指令，删掉了工具调用的日志标记，从而骗过了幻觉检测。
    - 作者还报告，检查函数对 agent 可见时，这种“目标作弊”更频繁。
    - 建议补一句：检查器不仅要只读，还应对 agent 不可见，不进入六个地方中的任何一个，也不放在 agent 可写的路径里。

18. **5.5 表 41（科研诚信机制）可以补三项。**
    - 验证缺口综述的数据：83% 的系统公开代码，但只有 38% 公开种子或执行轨迹，只有 38% 报告了新颖性验证方法。
    - 应补的三项机制：
      - 尝试次数与筛选策略的披露（防选择性报告）；
      - baseline 的出处；
      - 评审独立：评判者不能是生成者。

19. **协作规约里的“汇报带证据而非断言”（2.3（4））有大规模实证支持。**
    - 2605.29442 分析了 20,574 个真实会话：
      - 违反开发者约束 38.33%；
      - 不实的自我汇报 22.58%，其占比随时间显著上升；
      - 越权行动 10.20%；
      - 91.49% 的可见问题要靠开发者明确反驳才得到纠正。
    - 建议：完成声明也要像科研 agent 的论断一样绑定证据（测试日志、命令输出），并作为一项机制列入表 7“产出的真实”。

20. **第 6 章配置 agent 的访谈方式需要调整。**
    - 访谈本身就是“需求分多轮逐步给出”的场景。在这种场景下模型平均下降 39%，过早给出答案的也表现更差：答案出现在前 20% 轮次的得分 30.9，出现在最后 20% 的 64.4（2505.06120）。
    - 把需求合并成一份一次性给出，基本可以恢复，GPT-4o 为 90.9，完整单轮为 93.0。
    - 建议：
      - 配置 agent 先收集，后整合成一份文件，在新的上下文里再归类和放置；
      - 每轮重述已收集的内容，不依赖对话历史；
      - 不要边问边写卡片。

## 一、上下文文件与系统提示词的实证

### 1. Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?
- **作者与出处**：Gloaguen, Mündler-Sasahara, Müller, Raychev, Vechev（ETH SRI）。arXiv 2026-02-12，v3 2026-09-29。
- **链接**：https://arxiv.org/abs/2602.11988
- **本地文件**：`reference/papers/2602.11988-evaluating-agents-md.pdf`
- **做了什么**：作者构建了 CTXbench，从 12 个已有开发者上下文文件的 Python 仓库中取出 138 个任务，另用 SWE-bench Lite 的 300 个任务。比较三种设置：无上下文文件、LLM 生成的文件、开发者手写的文件。测试的 agent 包括 Claude Code + Sonnet-4.5、Codex + GPT-5.2 / GPT-5.1 mini、Qwen Code + Qwen3-30b-coder。之后分析执行轨迹，看指令是否被遵守、概览是否有用。
- **关键发现**：
  - LLM 生成的文件：SWE-bench −0.5%（p=0.87），CTXbench −2%（p=0.37）。
  - 开发者文件：平均 +2.4%（相对无文件 p=0.21，相对 LLM 生成 p=0.038）。
  - 成本：步数分别 +2.45 和 +3.92，成本 +20% 和 +23%（p<0.001）。GPT-5.2 的推理 token +22%。
  - 指令被严格遵守：文件提到 uv 时每个任务平均使用 1.6 次，未提到时不到 0.01 次。
  - 概览不帮助更快找到相关文件。Sonnet-4.5 生成的文件 100% 含概览。
  - 删掉 README 和文档后，LLM 生成的文件平均 +2.7%，并超过开发者手写的文件。
  - 作者的建议：暂时不用 LLM 生成的文件；手写文件只放 README 里没有的内容，并且先评测再采用。
- **文档**：
  - 支持 3.1“只写模型默认做不对的”。
  - 4.4 的淘汰补第二条线：删除复述环境的内容。

### 9. Design Patterns for Securing LLM Agents against Prompt Injections
- **作者与出处**：Beurer-Kellner, Buesser, Creţu, Debenedetti, …, Tramèr, Volhejn（IBM、Invariant Labs、ETH、Google、Microsoft 等）。arXiv 2025-06-10。
- **链接**：https://arxiv.org/abs/2506.08837
- **本地文件**：`reference/papers/2506.08837-prompt-injection-design-patterns.pdf`
- **做了什么**：论证在现有 LLM 上，通用 agent 无法得到可靠的注入防护。提出六种面向具体应用、以限制能力为代价的设计模式，并给出 10 个案例，包括 SWE agent、邮件日历、医疗等。核心原则：agent 读入不可信内容之后，这些内容在任何情况下都不能触发有后果的动作。
- **关键发现**（定性，无基准数字）：
  - 六种模式：
    - Action-Selector；
    - Plan-Then-Execute：读取不可信数据之前先定好计划；
    - LLM Map-Reduce：隔离的子 agent 各处理一份不可信数据；
    - Dual LLM：特权 LLM 从不看到不可信原文，隔离的 LLM 没有工具；
    - Code-Then-Execute：即 CaMeL 的做法；
    - Context-Minimization：不再需要的早先上下文直接删掉。
  - 提示词层面的防御、分隔符和检测器都是启发式的，不提供保证。
  - 让用户确认会带来审阅疲劳。SWE 案例里，agent 没有直接下载恶意包，而是在代码里加一行 import，让用户自己去装。
- **文档**：
  - 表 7、31、44 的“来源标注”机制应换成隔离模式。
  - 5.3 科研 agent 读论文和网页的环节，应明确用 Plan-Then-Execute 加 Map-Reduce。
- **builder**：
  - 工具卡片加两个标志：“读不可信数据”和“有外部副作用”。两者同时出现在一个上下文里、又没有隔离模式时报警，并建议具体模式。
- **agent**：访谈时追问“哪些工具会读外部内容，哪些有副作用”，据此选定安全模式。

### 14. Agent Workflow Memory (AWM)
- **作者与出处**：Wang, Mao, Fried, Neubig（CMU、MIT）。arXiv 2024-09-11。ICML 2025。
- **链接**：https://arxiv.org/abs/2409.07429
- **本地文件**：`reference/papers/2409.07429-agent-workflow-memory.pdf`
- **做了什么**：从成功的轨迹中归纳出可复用的子任务流程，具体值换成占位符（如 `{product-name}`），作为记忆注入，通常放进系统提示词。有两种用法：离线时从训练样例中学；在线时从测试流中学，只保留由 LLM 评判为成功的运行。
- **关键发现**：
  - WebArena（GPT-4）成功率 35.5%，基线 BrowserGym 23.5%，即 +12.0 个点、相对 +51.1%。也超过使用 14 条人写流程的 SteP（33.0%）。
  - 在 Mind2Web 上，抽象的流程比检索具体范例好：元素准确率 +5.0，步骤成功率 +4.0。

  - 支持把“做法”和“预防性规则”写成子任务级、带占位符的抽象例程。
  - 2.3（3）的“范例”需要细化。
  - 它的在线学习只有 LLM 评判把关，学到的错误流程有害，这反过来支持人工审批。
- **builder**：
  - 做法卡片模板：目标、带占位符的步骤、何时偏离。
  - lint：出现了本该参数化的具体值时提示。
- **agent**：从用户过去的会话中提炼子任务流程卡片，放进待审区。

### 17. Revoked but Still Authoritative: An Empirical Study of Revocation Enforcement in Agent-Memory Systems
- **作者与出处**：Shen, Toyoda, Leung（Vulcan Research、AIFT）。arXiv 2026-09-08。预印本。
- **链接**：https://arxiv.org/abs/2609.08258

    - 输出过滤：18.1%，而且这是在事先知道被撤销文本的条件下。

  - 4.4 的“标记失效”需要加执行机制，见上文“矛盾与补充”第 5 条。
  - 3.3“提示词只是引导”又多一个例证。

- **做了什么**：在 3 个任务上构造写入不同需求子集的提示词（8.4k 个数据点），测量需求写与不写时的表现，以及在模型版本之间的稳定性。提出“感知需求”的提示词优化方法。
- **关键发现**：
  - 未写的需求平均低 22.6%，但 41.1% 的情况下模型仍能猜对（准确率 ≥98%）。
  - 按类型分：格式类需求猜中 70.7%，条件类只有 22.9%。
  - 真实开发者提示词里的需求，65.2% 本来就能猜中。
  - 稳定性：
    - 跨提示词，未写需求的标准差 8.9%，是写了的 2 倍多；
    - 跨模型更新，22.9% 的情况退化；5.9% 的未写需求下降超过 20%，约为写了的 2 倍；
    - 同一模型的快照更新（gpt-4o 05-13→08-06）也会造成退化。
  - 把需求全部写上可能下降 19%。
  - 感知需求的优化 +4.8%，挑选要写的需求后提示词短了 43%。
- **文档**：见上文“矛盾与补充”第 7 条和第 12 条。
- **builder**：
  - 卡片增加“正文已删、检查项保留”状态，表示该项已被模型默认值覆盖。
  - 每次模型变更都跑全部检查，包括已删除正文的项。
- **agent**：
  - 访谈时主动挖掘条件类需求。
  - 决定写哪些需求时，先测一遍哪些已经被默认猜中。

### 23. Model Context Protocol (MCP) Tool Descriptions Are Smelly! Towards Improving AI Agent Efficiency with Augmented MCP Tool Descriptions
- **作者与出处**：Hasan et al.（含 Hassan, A. E.）。arXiv 2026-02-16，v3 2026-05-31。
- **链接**：https://arxiv.org/abs/2602.14878
- **本地文件**：`reference/papers/2602.14878-mcp-tool-descriptions-smelly.pdf`
- **做了什么**：从官方和社区指南中归纳出工具描述的六个组成部分，制定评分标准，做成基于 LLM 的坏味道检测器。在 MCP-Universe 上测试补全描述的效果，并对六个部分做消融。
- **关键发现**：
  - 六个部分：用途、何时与如何使用、限制、参数说明、长度与完整性（3–4 句以上）、示例。
  - 103 个 MCP 服务器、856 个工具：97.1% 至少有一种坏味道，56% 用途不清。

- **文档**：见上文“矛盾与补充”第 10 条。2.3（6）和表 11 的“工具定义”可以细化为这六个部分。
- **builder**：
  - 工具卡片按六个部分设字段，带坏味道 lint：缺用途、缺限制、参数格式不清。
  - 每个字段可以单独开关做消融，并显示 token 和步数成本。
- **agent**：写工具描述时按六个部分逐项填写，写完用坏味道扫描作为检查项。

### 24. Autonomous Research Agents: A Survey of AI Scientists and the Verification Gap
- **作者与出处**：Ding et al.。arXiv 2026-06-29。
- **链接**：https://arxiv.org/abs/2608.05179
- **本地文件**：`reference/papers/2608.05179-research-agents-verification-gap.pdf`
- **做了什么**：从 125 篇候选中筛出 35 篇，完整编码其中 26 篇（24 个可运行系统）。审计维度有七个：生命周期阶段、自主程度、评测方式、公开了哪些产物、人在回路的节点、新颖性验证、结果筛选的披露。核心论点是：论断比代码更难验证。
- **关键发现**：
  - 83% 公开代码，71% 公开提示词，但只有 38% 公开种子或执行轨迹，只有 38% 报告新颖性验证方法。

  - 提示词和上下文工程是“没有记录的变量”。文中提到，仅格式变化就能造成多达 76 个点的波动。
  - 作者提醒：编码员在自主程度、新颖性、筛选三项上的一致率只有 50%–65%，相关比例只代表方向。
- **文档**：
  - 5.5 表 41 补三项机制。
  - 4.4 补“复用时重验”。
  - 4.6 补“每次运行附带上下文清单”，即记录本次实际编译出的上下文。
- **builder**：每次运行附带编译产物的版本号与清单（manifest），使“上下文”变成有记录的变量。

## 九、编写、评测与组织提示词的工具

### 25. Who Validates the Validators? Aligning LLM-Assisted Evaluation of LLM Outputs with Human Preferences（EvalGen）
- **作者与出处**：Shankar, Zamfirescu-Pereira, Hartmann, Parameswaran, Arawjo。arXiv 2024-04-18。UIST 2024（ACM DOI 10.1145/3654777.3676450）。
- **链接**：https://arxiv.org/abs/2404.12272
- **本地文件**：`reference/papers/2404.12272-evalgen-who-validates-validators.pdf`
- **做了什么**：一个混合主导的评测工具，集成在 ChainForge 中。LLM 提出评判标准和候选断言（Python 函数或 LLM 评分提示），人给一部分输出打分，系统据此挑出与人的打分最一致的断言。
- **关键发现**：
  - 用户研究 n=9，都是业界从业者。
  - 与 SPADE 对比：
    - 产品场景：一致度 66.46% 对 54.35%，断言数 4 对 9；
    - 医疗场景：一致度相同，都是 48.29%，断言数 3 对 5。
  - 核心发现是“标准漂移”：需要标准才能给输出打分，而打分的过程又在定义标准，不可能在人看过输出之前把标准完全定下来。参与者会回头修改先前的打分。
- **文档**：见上文“矛盾与补充”第 8 条，修订 4.4“先写检查项再写正文”。
- **builder**：
  - 检查项编辑器旁边放输出采样和打分面板。打分结果反过来修订检查集，并显示检查与人工打分的一致率。
  - 检查项要有版本号。
- **agent**：配置 agent 不要求设计者一次说全所有标准，而是先展示样例输出让他们打分，再据此归纳出检查项。

### 26. Prompt Orchestration Markup Language (POML)
- **作者与出处**：Zhang Yuge et al.（Microsoft）。arXiv 2025-08-19。
- **链接**：https://arxiv.org/abs/2508.13948
- **本地文件**：`reference/papers/2508.13948-poml-prompt-markup.pdf`
- **做了什么**：一种类似 HTML 的提示词标记语言，组件分三类：
  - 意图组件：`<role>`、`<task>`、`<example>` 等；
  - 数据组件：`<document>`、`<table>`、`<folder>`、`<image>` 等；
  - 结构组件。
  
  用独立的 `<stylesheet>` 把呈现格式与内容分开。配有模板、VS Code 扩展（悬停提示、诊断、预览）和多语言 SDK。
- **关键发现**：
  - 在 TableQA 上，只改呈现格式，GPT-3.5 Turbo 就从 0.060 变到 0.558（+929%），Phi-3 Medium 提升 4450%。最优格式因模型而异。
  - 用户研究只有 7 人，数据组件和工具链最受认可。
- **文档**：3.1“另有四点影响效果”可以补“格式”一点：呈现格式本身就会大幅改变效果，因此要按模型评测。
- **builder**：这是最接近我们“卡片 → 编译”设计的已有工作，可以参考：
  - 内容卡片与按模型的渲染样式分离；
  - 诊断与预览；
  - 渲染样式本身作为一个消融变量。
- **agent**：无。
