# 调研：context engineering 相关文献

2026-10-03 整理。目的有两个：一是核对 `docs/Agent Context.md` 引用的文献是否支撑文中的说法，二是找文档没覆盖到、对 docs、builder、agent 有用的新研究。

## 这里有什么

```
reference/
├── README.md                 本文：结论汇总
├── notes/cited-papers.md     核对文档已引用的 56 条文献，逐条判定准确与否
├── notes/new-papers.md       文档未引用的 26 篇新论文，逐篇写对三部分的用处
└── papers/                   47 篇 PDF（已引用 21 篇 + 新增 26 篇），文件名 <arxiv-id>-<简称>.pdf
```

两份笔记由两个调研 agent 读原文写成，数字都标了出处。我从 9 篇论文里抽了十几个关键数字回原文 PDF 核对，全部对得上，包括 Agents4Science、SciIntegrity-Bench、ManyIH、IHEval、Revoked、AGENTS.md 评测等。其余没有逐个复核，用于写文档前请再查原文。只收录开放获取的论文；博客和官方文档没有下载，链接在笔记里。

## 一句话结论

文档的大方向得到了外部证据的支持：常驻越少越好；条件性内容按需加载；硬规则要交给机制；agent 写的内容要经人审。

但有一个前提被证据推翻了：**模型能按来源的效力顺序自己裁决冲突。** 证据显示它做不到，告诉它"按层级优先"也没用。这意味着冲突裁决、失效过滤、去重这些事，应该在编译时由 builder 做掉，而不是写进上下文指望模型照办。这一条同时改变 docs 和 builder 的设计，是这次调研最重要的发现。

## 二、对文档：方法层面要重新想的地方

以下不是改错，而是证据要求方法本身调整。按影响大小排列，括号里是证据来源。

1. **冲突在编译时裁决，不交给模型**（IHEval 2502.08745、Control Illusion 2502.15851）
   - 有冲突时，各模型的准确率只有 14%–70%。
   - 明确告诉模型"按层级优先"，GPT-4o 从 70.0 降到 67.2。
   - 模型听措辞更严厉的一方，也听"专家共识""CEO 要求"这类说法。
   - 因此 2.2 的冲突规则（来源不同看来源、来源相同看条件）应改成**由 builder 或配置 agent 在编译时执行**，上下文里只放裁决后的结果。
   - 3.2 的"块首写效力声明"降为弱辅助。运行时才出现的冲突（用户当前请求对上锁定项）交给机制。
   - "有效力的层级不多于三层"仍可保留，但要写明这是设计取舍：层级少是必要条件，不是充分条件。

2. **"失效"必须由机制执行**（Revoked but Still Authoritative 2609.08258）
   - 被撤销的事实全部仍被检索出来，agent 因此执行不安全动作的比例是 43.1%。
   - 在提示词里要求忽略这些事实，只降到 37.2%；在存储层过滤，降到 0/1620。
   - 4.4 的"标记失效而非抹去"要补一句：失效条目在进入上下文之前过滤掉；新条目写明它取代了谁。

3. **淘汰沿三条线，删的是正文，检查项要留下**（AGENTS.md 评测 2602.11988、What Prompts Don't Say 2505.13360、Codified Context 2602.20478）
   - 第一条，复述模型默认值的删（文档已有）。
   - 第二条，复述环境里已有信息（README、代码）的也删。LLM 生成的上下文文件让成功率下降、成本上升 20% 以上。
   - 第三条，环境变了要更新：规格随代码漂移是真实项目里主要的失效方式。
   - 不写的需求在模型更新后退化的概率约是写了的 2 倍，静默快照更新也会触发。所以正文可以删，检查项要留着，每次模型变化都要重跑。

4. **检查项先写草稿，看过输出再修订**（EvalGen 2404.12272）
   - 人要先看过输出、动手打分，才能确定评判标准，这叫"标准漂移"。
   - 4.4 的"先写检查项再写正文"改为：检查项先起草，看过真实输出后修订，并且要有版本。

5. **硬规则在会话里会衰减，要用提醒重申**（配置文件因子实验 2605.10039）
   - 在 25–500 行范围内，文件大小和指令位置都没有可检出的效应。
   - 但会话内衰减明显：每多生成一个函数，遵守的几率乘以 0.944。
   - 3.1 的位置论证要限定在"指令多、上下文长"的场景。运行时提醒除了状态和催促，还应补上"硬规则重申"。

6. **"来源标注"不是机制**（Design Patterns 2506.08837、记忆投毒 2606.04329）
   - 表 7、31、44 把来源标注列为"外部内容是数据"的兜底机制，不成立；分隔符和标签只是启发式手段。
   - 真正的机制是隔离：先定计划再读不可信数据、特权模型不看原文，等等。
   - 常驻的记忆索引和压缩摘要都是投毒通道。把记忆装进系统提示词的 agent，投毒生效率是 64.7%，只通过工具读取的是 17.4%；经由压缩的投毒成功率高达 85%。
   - 常驻索引只收已审批的条目；压缩摘要要保留来源标签。

7. **经验模块的证据比文档写的更弱**（2606.15017、Dynamic Cheatsheet [38]、AgentRxiv [40]）
   - 在相同 token 预算下，ReasoningBank 等记忆模块都没有赢过不带模块的基线。WebArena 上 39.33% 对 44.78%。
   - 文档引 [37][38][40] 来支撑"严把写入"，但这三篇的结论主要是正面的；能支撑"错误被照抄"的直接证据只有 [39]。
   - 5.5 应该正面回应这些结果，并加一条规则：任何记忆模块都要和同预算的基线比过再上线。

8. **几条写法建议要加限定**
   - "范例比规则清单有效"证据有分歧：输出格式类内容用范例；流程类内容用带占位符的抽象例程（AWM、GEPA）。
   - 工具描述里去掉示例从未显著降低表现；把描述写全会让执行步数增加 67%（MCP 工具描述研究 2602.14878）。
   - 压缩摘要模板应当可评测、可调，并加一段"关键变量与运行时值"（ACON 2510.00615）。

9. **Claude Code 的压缩行为与文档设计有冲突**（[28]）
   - 压缩后，**skill 目录不会重新注入**；只有已调用过的 skill 正文保留，每个 5k、总计 25k。
   - 文档"目录常驻、正文触发"的设计，在 Claude Code 上需要框架自己在压缩后重新注入目录。

## 三、对 builder：功能清单

已经做了的一项：
- skill 的预算改成 Agent Skills 开放规范的值：描述 1024 字符（原先用的是 Claude Code 自己的 1536）、正文 500 行、约 5000 token。
- 因为 builder 的输出不绑定 harness，取各家里最严的值。改在 `template/default.yaml`。

建议按这个顺序加：

| 功能 | 依据 | 难度 |
| --- | --- | --- |
| **lint 规则**：已交给机制的规则不该再写进提示词；有适用条件的内容却编译进了常驻；常驻文件超行数；引用资料没写用途；强调词密度过高 | 配置坏味道 2606.15828（100 个仓库里 91 个有问题）；系统提示词研究 2609.31575；IHEval | 低 |
| **卡片的"取代"与"失效"字段**：失效卡片不编译，取代关系写明 | Revoked 2609.08258 | 低 |
| **"会话中需重申"属性**：硬规则可勾选，编译出一条运行时提醒 | 因子实验 2605.10039 | 低 |
| **变更记录**：每次编译与上次比较，显示哪些文件改了多少字 | 真实仓库里只有 21.9% 的提示词变更有记录（2412.17298）；2609.31575 | 中 |
| **冲突检查**：同一条目、同一条件下有多张卡片时提示；以后由 agent 做语义冲突检查 | IHEval；坏味道 | 中 |
| **与项目文档重复的检测** | AGENTS.md 评测 2602.11988 | 中，要读 agent 的工作目录 |
| **卡片绑定代码路径**：被绑定的路径变动时提醒更新 | Codified Context 2602.20478 | 中 |
| **检查项的采样打分**：贴几条真实输出，人打分，修订检查项 | EvalGen 2404.12272 | 高，属于评测夹具 |
| **单卡片消融**：带和不带这张卡片，比较成功率与 token | AGENTS.md 评测；What Prompts Don't Say | 高，需要接 harness 跑 |
| **按模型的渲染样式**：同一组卡片，可以为不同模型渲染成不同格式 | POML 2508.13948：只改格式，效果可差数倍 | 高 |

另外，POML 是目前最接近"卡片 → 编译"思路的已有工作：内容与呈现分离，有诊断和预览。值得细看它的设计。

## 四、对配置 agent

- **没有直接先例。** 没有找到"帮人配置另一个 agent"的高质量研究。现有工作要么是自动搜索 agent 设计（ADAS 一类），要么是一般的需求访谈（LLMREI 2507.02564，可参考）。这说明第 6 章有独创性，也意味着没有现成答案可抄。
- **访谈要先收集、后整合。** 需求分多轮给出时，模型的表现平均下降 39%；把需求合并成一份一次性给出，基本能恢复（2505.06120）。所以配置 agent 应该先收集，再整合成一份文件，然后在新的上下文里归类和放置；不要边问边写卡片。
- **只做最小增量，并配评测。** LLM 生成的整篇上下文文件没有收益，还增加成本（2602.11988）。这直接支撑"它起草，人审批"。
- **重点挖条件类需求。** 这类需求模型只能猜对 22.9%（2505.13360）。访谈要专门问"什么情形下要不一样"。
- **检查项通过打分归纳。** 先给设计者看样例输出、让他打分，再归纳检查项，不要求他一次说全（EvalGen）。
- **交付前自查跑 builder 的 lint**（配置坏味道）。
